三、这一轮解决的核心问题：304 空响应
════════════════════════════════════════════════

现象：一部分小资源（图标、头像、道具格子）每次进都重新拉，日志里是
      MISS 27-50ms 0B，而且同一个 URL 连续几次都是 0 字节，永远补不进库。

根因：
  客户端发请求时带 If-Modified-Since 条件头 → 上游回 304 Not Modified
  （空正文，不重发内容）→ 代理把这空 304 原样转发给客户端 → 但客户端
  本地其实没有这份文件，拿到空内容 → 重试 → 又是 304 → 死循环。

  实测验证：给同一个 URL 带 If-Modified-Since: 2031 年，上游返回 304 +
  0 字节；不带这个头，返回 200 + 2339 字节。

修复：回源时剥掉 If-Modified-Since / If-None-Match / If-Range 三个条件头，
      强制上游返回 200 完整正文，本地才有东西可存。若上游仍然回 304 而
      本地无副本，自动改用无条件 GET 重取一次。

修复前：item_003_1.swf 等资源 3 次请求全是 0B，永久不命中
修复后：同样请求（带 2031 年的 If-Modified-Since）返回 200 + 2339B，存库成功

这是冲 100% 命中率的最后一个硬骨头，现在啃掉了。

四、命中率天花板的说明
════════════════════════════════════════════════

res_config 清单只覆盖启动必需的 5264 个资源。但客户端还会按需请求一批
清单里根本没有的资源，已发现 682 个，主要是：

    resource/swf/*                449 个（武器图标、道具图标、展示图）
    resources/accessory/*          27 个（挂饰模型）
    resources/lobbyPlayerAnim/*    27 个（大厅角色动画 ← 你说的"左边角色 ui 一动一动"）
    resources/ui/*                 22 个
    resources/playerAnim/*         20 个（角色动作包）
    resources/weapon/*              20 个（武器模型）

这些是服务端下发的动态内容，本地无法提前枚举。对策是「玩一局、补一局」：

  每次服务以 daemon 方式启动时，会在后台静默跑一次 cover：
  读上一局的 local_cdn.log，把客户端实际请求过、但本地缺失的资源补下来。
  所以第一局玩到什么，第二局进去那些就全是本地命中。

  这个补齐是后台线程，不阻塞启动、失败也不影响使用。

如果想让某个页面第一次进就不等，先在游戏里点开一次，再跑
大厅资源-补齐缺失.bat，之后就是毫秒级了。

五、帧率的结论：别改，没用
════════════════════════════════════════════════

大厅是 24fps，这是 SWF 头的值，客户端代码里没有任何 stage.frameRate 赋值
（SWF 里唯一一处 stage.frameRate = 12 是 com.junkbyte.console 的帮助文本）。

三条路都试过，全部不通：

  1. 改 SWF 头帧率 → 客户端卡死。ModuleLoader.as:124-134 会拿文件名里的
     32 位 md5 校验内容，改了就重载，5 次后 AirLobbyPreloader 停在 178MB
     不再发任何请求，静默 100 秒以上。

  2. 改 AIR 描述符 <frameRate>60</frameRate> → 确实生效了，但：
       24fps 空闲 CPU  1.4%
       60fps 空闲 CPU 24.6%   ← 涨 18 倍
     视觉上零可感知差别。属于纯亏。

  3. 改缓动曲线 → 要动 DoABC 字节码，同样触发 md5 校验，同上。

  顺带确认：大厅用 GreenSock TweenMax，缓动曲线分布是 Back 501 处、
  Strong 151 处、Expo 33 处、Linear 只有 4 处。Back 是"过冲到目标再弹回"
  的曲线，大量 UI 元素同时进出、每个都回弹，整体观感就会毛躁——那才是
  "不够丝滑"的真正来源，不是帧率。这个改不了，它在编译后的字节码里。

战斗端帧率才是有意义的：进游戏设置里能调到 60-200
（GameSetting.cs:25-27, FrameLimitMin=60 / FrameLimitMax=200）。

七、已知限制
════════════════════════════════════════════════

1. 443 是纯 TCP 透传。globalResurl 是 https://cdn.4399ssjj.com/global_air，
   走 443 的资源命中不了本地库，本地无法加速（TLS 由真 CDN 终结）。
   要加速得做 MITM 装自签根证书，风险和收益不成比例，不做。

2. /ecs/* 是战斗端更新通道（增量补丁、版本号），故意不缓存——缓存住会
   导致版本升级时拿到旧补丁。它不计入覆盖率统计。

3. gameguard/update.cfg 不缓存：带 id= 参数，内容每次加密不同。

4. 战斗资源（AssetBundle）是另一条链路，不走 local_cdn：
   %LOCALAPPDATA%\Wooduan\Preload  19.5 GB / 19244 个包，清单 17722 个
   bundle 缺失 0。客户端自己读本地缓存。

5. 日志超过 8 MB 自动轮转，保留 local_cdn.log.1 / .2 两代。

6. 如果启动器更新了客户端版本，paras.dat 里的 lobbyFileName 会变，
   res_config 清单的 md5 也会变。届时重跑一次 大厅资源-补齐缺失.bat 即可。

十、2026-11-23 晚：修掉「打开就下载/慢」的真凶
--------------------------------------------
现象：开游戏就下载资源、点什么都慢。
根因：443 的 MITM 一直没接上。mitm.enabled() 里探证书靠 subprocess 调 certutil
      解析输出，打包成 --noconsole 的 exe 后拿不稳 -> 假阴性 -> mitm.enabled()
      恒 False -> 所有 https 资源走盲透传、从不落盘、每次开游戏都真下载。
      证据：/__stats__ 里 https 一直涨而 https_mitm 恒 0。

已修（都在源码里，exe 已重新打包部署）：
1. 探证书改成读注册表
   HKCU/HKLM\Software\Microsoft\SystemCertificates\Root\Certificates\<缩略码>，
   certutil 只作兜底。实测 35ms，打包环境不再假阴性。
2. mitm.enabled() 加 3 秒缓存；local_cdn.handle_https() 入站/出站都设 TCP_NODELAY。
3. 443 上游连接按 (ip, host) 复用（原来每个未命中都新建 TLS），
   serve_conn 支持同一条 TLS 连接连拉多个请求。实测 5 个图标：45ms + 1ms*4。
4. POST/PUT 请求体一律原样转发（以前会被当 GET 发出去，接口会失灵）。
5. 新增启动接口短缓存 _dyn（TTL 600 秒，SSJJ_DYN_TTL=0 关闭）：
   /ecs/*/update.php 1244ms -> 18ms
   /s10/lobby.php     1892ms -> 4ms
   http 和 https 两条路都接。python local_cdn.py dyncache / dyncache clear
6. /ecs/ 的 22.3MB 补丁包已进白名单：23MB 从「每次启动 3 秒」变成 33ms 本地命中。

现状：风险模式开启中（大厅缓动变体 + 注入守护 + 443 MITM），
      80/443 由 生死狙击工具箱.exe --accel-daemon 提供。
      第一次开游戏仍会把 https 资源拉一遍（同时落盘），第二次起才是秒开。

十一、2026-11-24 凌晨：三个真问题的修法

1. 只开注入不再要求先开总开关
   inject_start() / inject_stop() / inject_state() 与总开关解耦，
   界面注入卡第一行就是「只开注入守护」；工具箱重启时若总开关关着但
   inject.enabled=True，也会单独把守护拉起来。

2. 权限不再甩一句「需要管理员权限」
   risk/privilege.py 开 SeDebugPrivilege；injector._open_target() 先试最小权限
   (0x043A) 再退 ALL_ACCESS，只有真拿到错误 5 才抛 NeedAdmin；
   守护撞权限会拉起提权副本 `工具箱.exe --risk-inject <pid>`（结果写
   risk_inject_result.json 由主界面读），界面有「以管理员重启」按钮。
   顺带修掉 EnumProcessModulesEx 报 299 把整次注入打断的 bug（现在重试 6 次）。

3. 退出卡死：证据 + 三层修
   看门狗抓到 23:06:43 MicroClient 无响应 56.5 秒，战斗端 23:07:34 退出后
   immediately 恢复；cdb 打开 dump 显示 UI 线程停在
   user32!DispatchMessageWorker -> MicroClient+0xcba08 -> ws2_32!select
   -> mswsock!WSPSelect -> SockWaitForSingleObject
   —— 即 MicroClient 在窗口消息处理里同步 select() 等对端，客户端能做的是：
   a) patch AceClientManager.Exit（它 Abort 原生 tick 线程再原生登出，是退出最硬的一步）
   b) Patch() 保存原字节，ProcessExit 时 RestoreAll() 写回（以前改了就回不去）
   c) PatchGuardType 加 BannedPatchName 黑名单，Start/Loop/Tick/Run/Update 一律不碰
   d) 工具箱自身 aboutToQuit → 1.5 秒后 os._exit(0) 兜底

4. 风控 3 分钟的真因：ACE 上报被打掉
   以前 patch 19 个方法，含 LoginSucc / ReceiveData / SendReport ——
   服务端看到「这客户端不汇报」就判第三方。现在默认 ace_mode=teardown，
   只 patch Exit / eixt_ace / user_loginOff_ace / Close 四个退出清理，
   登录心跳上报全部放行。要回老行为：%LOCALAPPDATA%\ssjj-toolbox\risk_ace_full.txt
   放一行 full（界面上是「ACE 策略」下拉框）。

5. 「不热加载但更安全」= 三档
   档0 只开加速/本地化/皮肤包预取（零进程接触，风控无风险）
   档1 推荐：注入 + 冷加载 + ACE teardown + 退出还原（一次性改内存，之后线程只
        每 10 秒 stat 一次配置，不碰游戏对象）
   档2 只在离线/私服：注入 + 热加载 + ACE full
   冷加载默认开（inject.cold_swap=True），改规则要重进一局才生效。
   WeaponSwapper 主线程热路径只是字典查表，效果靠 IL Hook 在武器创建瞬间生效。

实测：livetest 注入成功 → 自检 patch 8 处、ACE teardown 4 个、冷加载 rules=3、
     4 个 IL Hook 全装上；只开注入（总开关 False）1 秒内注入且总开关保持 False；
